# Vistella / MultiDoc — 工程契约（永久）

> **地位**：本文件是本项目**最高约束**。任何 AI、开发者、自动化脚本，在修改 `src/` 之前必须先读本文件。
> **优先级**：本文件 > 任务清单 > 单次对话中的临时决定 > 代码里的旧注释。
> **机器可执行部分**：标 `⟦CI⟧` 的条目由 `tools/check_contracts.py` 强制检查，构建时自动运行，**不允许跳过**。
> **建立日期**：2026-10-26　　**依据**：2026-10-26 全项目代码审计（394 条缺陷 / 34 条 P0，见 `docs/CODE_AUDIT_2026-10-26.md` 与 `audit/`）
> **修订规则**：本文件只能由用户拍板后修改。任何 AI 不得自行放宽本文件的任何一条。

---

## 0. 为什么会有这份文件

审计发现的问题不是随机分布的，而是**同一种工作方式的产物**。核心失效模式有三个：

1. **交付单位错了** —— 交付的是"一段代码"而不是"一件用户能用的能力"，于是"写完了"被当成"能用了"。
2. **验证方式无效** —— 测试断言的是自己写的代码的结构，81 个测试全绿却漏掉全部 P0。
3. **状态真相不唯一** —— 同一个语义有 2~3 份副本，靠手工 connect 同步，越加功能越容易失联。

本文件的作用，就是把这三条从"靠自觉"变成"有规则、有检查、有模板"。

## 1. 交付单位：一条用户能力路径

### 1.1 阶段开始前必须先写能力路径

任何阶段的第一个产物**不是代码任务清单，而是用户视角的完整操作步骤**。

**定义**：一条能力路径 = 用户从某个入口触发，经过若干操作，达到一个明确结果，**并且这个结果在退出/重开/撤销等边界条件下仍然成立**。

- ❌ 错误的任务单位：`实现 05-01，删除保存路径的 flattenText()`
- ✅ 正确的能力单位：
  ```
  打开带文字的 PNG → 用文字工具加文字 → Ctrl+S → 关闭文档 →
  从"最近"重开 → 文字仍在、仍可编辑、图层结构未变、源文件未被破坏
  ```

**规则 1.1**　能力路径必须**先写出来并被用户认可**，才允许开始改代码。

**规则 1.2**　能力路径的**每一步**都必须在验收清单（§4）里有对应条目。一条步骤没有验收条目 = 这条能力没做完。

### 1.2 阶段完成的判定：四道门禁

| 门 | 内容 | 通过标准 |
|---|---|---|
| **G1 构建** | 全量编译 | 零 warning（含第三方头） |
| **G2 能力** | 覆盖本阶段能力路径的端到端测试 | 全绿 |
| **G3 不变量** | 本阶段触及的数据/状态不变量测试（§7） | 全绿 |
| **G4 回归** | 全量 ctest + 涉及生命周期时的 ASAN 一轮 | 全绿 |

**规则 1.3**　四道门禁**全绿之前**，不得向用户询问"下一个阶段做什么"，不得宣布阶段完成。

**规则 1.4**　四道门禁全绿之后，必须先向用户**演示这条能力路径的实际操作**（截图或录屏），再谈下一阶段。

**规则 1.5**　任何"没问题 / 全绿 / 好了"的结论，必须**同时附带**：
- 本次验证覆盖了**哪几条用户路径**（逐条列出）
- 本次**没有验证什么**（盲区清单）

> 规则 1.5 不可省略。"全绿没问题"而不带覆盖范围的表述，等同于未验证。

## 2. 占位与跨阶段前置协议

> 对应审计模式 A（占位即完成，约 90 条）与模式 E（未完成的迁移，约 50 条）。

### 2.1 零调用者即不存在

**规则 2.1**　交付时新增的 public API，必须至少有一个**生产代码**调用点。只有测试调用的 API **视为未实现**，必须删除或在本阶段接上。

**⟦CI⟧ 规则 2.1a**　扫描 `src/` 下所有 public 方法/函数声明，若在 `src/` 中找不到调用点 → 报出，交由人工确认（注释掉的、纯虚、Qt 的 moc 接口需白名单）。

> **R1 的已知边界**（必须知道，否则会误信它）：
> - 统计调用点时**先剥离注释**，否则一条 `TODO` 标记里提到符号名就会伪造出"有调用者"，把真缺陷藏掉；
> - 声明行与定义行不算调用点（`void Foo::bar() {}` 不算一次调用）；
> - `&Class::method` 这种 PMF 用法（Qt `connect`）算调用；
> - **同名不同作用域无法区分**：`vistella::info` 与 `spdlog::info` 会被当成同一个符号，可能漏报；
> - 纯 Qt meta-object 调用（`QMetaObject::invokeMethod`）静态不可见，需白名单。
>
> 因此 R1 是**线索生成器**，不是判决书：报出来的必须人工确认，没报出来的不能当作"一定有人用"。

**规则 2.2**　**禁止 `return nullptr` 的兼容层**。deprecated shim 必须带 `[[deprecated]]`，并**在下一个阶段删除**。

### 2.2 跨阶段前置：必须登记 + 必须优先偿还

当某功能当前阶段需要调用某个函数，但该函数要到后续阶段才开发完整时：

**规则 2.3（登记）**　必须同时做三件事，缺一不可：

1. 代码处写明**缺什么**、**在哪个阶段补**，**必须**是下面这一行（`tools/check_contracts.py` 按此正则校验；写成多行或换分隔符会被判为格式错误）：
   ```cpp
   // TODO(P8.4): LayerStack::render() still falls back to the 8UC3 path, so 4-channel documents lose alpha -- see docs/DEBT.md#A-ALPHARENDER
   ```
   - `TODO(P<x.y>)` —— 阶段号，必须与 `docs/DEBT.md` 中该条的**建议阶段**一致；
   - 冒号之后 —— **还缺什么**，一句话说清缺的那部分，禁止只写"待实现"；
   - `-- see docs/DEBT.md#<ID>` —— 该条在登记表中的 ID，**逐字一致**；
   - 标记写在**出问题的那个声明/实现处**，不得堆在文件头。
2. 在 **`docs/DEBT.md`** 登记一行：ID、建议阶段、缺什么、影响哪些用户路径、验收方式、状态。
3. 标注**用户可见的影响**（例如"4 通道文档保存后丢 alpha"），不允许只写技术描述。

**⟦CI⟧ 规则 2.3a**　源码中出现的每个 `TODO(P<x.y>)` 必须在 `docs/DEBT.md` 中有对应登记项；反之，`DEBT.md` 中状态为 `open` 的条目，必须在源码中有对应的 `TODO` 标记（双向校验，防止登记表与源码脱节）。

**规则 2.4（偿还优先）**　进入阶段 P<x.y> 时，`docs/DEBT.md` 中所有**建议阶段** = P<x.y> 的 `open` 条目**必须优先完成**，排在当阶段新功能之前。`tools/check_contracts.py --stage P8.4` 会机械校验这一点：到期条目仍为 `open` → 报 ERROR。

**规则 2.5（禁止接口先行）**　只留接口、留 TODO 而**没有登记到 DEBT.md** 的，等同于没做。

### 2.3 迁移必须一次做完

**规则 2.6**　"引入新结构 → 留兼容层 → 迁移调用方 → 删除旧结构"这四步必须在**同一阶段内**完成。允许停在第二步的时间上限：**一个阶段**。到期未完成 → 记入 `DEBT.md` 并在阶段末汇报中显式列出。

## 3. 统一订阅模式：状态只广播，不点对点

> 对应审计模式 B（真相不唯一）与 §7.6（7 处状态副本、80+ 手工 connect）。

### 3.1 唯一 owner 原则

**规则 3.1**　每一个可观察状态，必须有且只有一个 **owner**。owner 持有真值并在其变更时发出通知。其他任何地方**只读不存**。

**规则 3.2**　引入新状态前必须回答三个问题，答不上来就不许引入：
1. 这个值和已有的哪个值**会不一致**？
2. 不一致时**谁是准的**？
3. 谁负责在 owner 变更时让其他副本失效？

**规则 3.3（禁止影子状态）**　系统级状态（窗口状态、输入法、剪贴板、主题）**只允许一个真源**，不得用成员变量镜像。例如窗口最大化状态真源必须是 `QWidget::windowState()`，不得另设 `m_mode`。

### 3.2 订阅模式

**规则 3.4**　状态传播必须走**统一广播通道**：
- owner 暴露一个变更信号（或统一的状态总线）
- 视图**订阅**该信号，在回调里**重读 owner 的真值**
- **禁止** view 与 view 之间直接 `connect`
- **禁止** view 自己缓存一份状态副本再手工同步

**规则 3.5（禁止重复刷新逻辑）**　"多处功能各自刷新同一块 UI"必须收敛成**单一刷新入口**。

**⟦CI⟧ 规则 3.5a**　扫描 `src/`：若同一段"刷新/重绘/更新"调用（例如 `renderToView()`、`invalidateCurrentCache()` + 重绘组合、`updateActionStates()`）在 **≥2 处**以**相同参数序列**出现 → 报出，要求收敛到单一入口。

**规则 3.6**　刷新必须**幂等**且**可合并**：同一事件循环内的多次刷新请求应合并为一次。

### 3.3 失效即删除

**规则 3.7**　owner 销毁时，订阅者必须自动解除订阅（`QPointer` / `QObject::destroyed` / scoped connection）。不允许用裸指针订阅。

## 4. 完整功能链验收清单

> 这是"一个功能做完了"的**完整**定义。规则 4.1 要求：**本节全部条目逐条回答，不得跳过**。
> 模板见 `docs/FUNC-ACCEPTANCE.md`。

### 4.1 入口与可达性

1. **入口在哪** —— 菜单项 / 工具栏按钮 / 快捷键 / 右键菜单 / 面板控件，逐一列出。
2. **什么场景下能用** —— 前置条件（有没有图层？有没有选区？文档类型？图像通道数？位深？），以及**不满足时应该怎样**（禁用并给出原因，而不是点了没反应）。
3. **怎么启动** —— 入口被点击后到功能真正生效，中间发生了什么。

### 4.2 操作与并发

4. **启动后怎么操作** —— 完整的操作序列，含边界输入（空选择、零宽高、单像素、超大图）。
5. **哪些操作会导致异常** —— 列出所有已知异常路径（除零、越界、空指针、类型不匹配、通道数不符、尺寸不符、文件不存在、磁盘满、只读目录）。
6. **异常了如何处理** —— 每条异常路径的**具体**表现：弹什么提示 / 状态栏写什么 / 是否可撤销 / 是否保留用户数据 / 是否回滚。**不允许**静默失败、不允许只写日志、不允许抛异常穿透 UI。
7. **启动该功能之后，哪些操作不被允许** —— 互斥关系（如涂抹模式下不能双击建字、变换中不能切图层）。必须是**代码强制**的，不是靠用户自觉。
8. **哪些操作可以同时进行** —— 并发/可交叠的操作（如拖滑块时能否旋转画布、能否切 tab），并说明状态如何合并。
9. **操作过程中系统的其它部分如何表现** —— 光标形状、状态栏、菜单 enable 状态、其它面板。

### 4.3 结果与数据变化

10. **操作之后应该有哪些表现** —— 视觉表现、控件状态、提示信息。
11. **操作完成之后哪些数据有哪些变化** —— 逐项列出：哪些内存数据变了、哪些持久化数据变了、哪些**不该**变。
12. **用户可见的变化有哪些** —— 与第 10 条的区别：这里是用户能观察到的差异（含"本该变化却没变"）。
13. **数据变化是否可逆** —— 哪些操作可以撤销，哪些不能。**不能撤销的必须在 UI 上明确告知**。

### 4.4 撤销 / 重做

14. **操作之后撤销，再 redo，操作能否重新回来** —— 必须**实际验证过**，不是推断。涉及异步渲染的，必须等回调完成后验证。

### 4.5 持久化与生命周期

15. **操作完成不保存直接关闭软件，或者强制关闭（kill）重启之后，打开的文件应该是什么状态**：
    - 不保存直接关闭 → 未保存的修改**必须丢得干净**，且不能留下半截文件
    - 强制 kill 后重启 → 要么自动恢复到崩溃前，要么明确提示"已丢失未保存修改"，**不允许静默**
    - 两种情况下的**原始文件**都**不得被破坏**
16. **保存如何处理**：
    - 直接写入源文件，还是建立新文件？
    - 还是新增图层 / 写入工程文件？
    - 写的是哪一份数据（当前合成结果？分层数据？活动图层？）
    - 保存过程中崩溃，原文件是否完好？
17. **最终保存如何处理** —— 存成什么格式、损失什么（分层？蒙版？文字可编辑性？ICC？元数据？），以及**这个损失是否在 UI 上告知过用户**。

### 4.6 边界与规模

18. **规模边界** —— 文档尺寸、通道数、位深、图层数、选区形状下的行为；超出支持范围时的表现。

**规则 4.1**　上述 18 项**逐条回答**。确实不适用的，写"不适用 + 理由"，**不允许留空**。
**规则 4.2**　第 14、15、16 项必须有**实际执行的验证**，不能只靠代码推理。
**规则 4.3**　验收清单是交付物的一部分，必须随代码一起提交（填好的版本进 `docs/acceptance/`）。

## 5. 测试规范

> 对应审计模式 D（验证方式无效）。

**规则 5.1（禁止回声测试）**　禁止只断言"结构存在""转发次数""cursor() 返回什么""某方法被调用 N 次"。这类测试在实现完全错误时依然会绿。

**规则 5.2（强制破坏自检）**　每个新测试写完后，**必须故意改坏实现一次，确认测试变红**，然后改回。
**没做过这个自检的测试，不许提交。**　自检次数必须写进提交信息。

**规则 5.3（按能力组织）**　测试按**用户能力路径**命名与组织，不按类。
`tests/tst_Path_SaveReopen.cpp`、`tests/tst_Path_LayerUndoRedo.cpp`、`tests/tst_Path_QuitSaves.cpp`。
文件名必须以 `tst_Path_` 或 `tst_Unit_` 开头。

**规则 5.4（声明保护对象）**　每个测试必须声明它保护的不变量与所属路径：
```cpp
// protects: m_current is a read-only render output, never a write target
// path:   open PNG -> brush stroke -> toggle layer visibility -> stroke still visible
```

**规则 5.5（生命周期改动必须过 ASAN）**　凡触及 `invokeMethod` 的 context、裸指针、跨窗口移动、`deleteLater`、异步回调的改动，一律加 ASAN 跑一轮。

**规则 5.6（禁止测试给死代码背书）**　只有 tests 调用的 API（`LayerMaskRenderer`、`ImageProcessorAsync` 等）→ 测试要么删，要么把生产链路接上。

**规则 5.7（阶段验收测试）**　每个阶段至少新增 **1 个 `tst_Path_` 端到端测试**覆盖本阶段能力路径。纯单元测试不算。

**规则 5.8（能力路径测试基座）**　`tst_Path_*` 统一使用 `tests/support/PathHarness.h`：
- `makeTestImage()` / `writeTestImage()` —— 合成**确定性**测试图（四象限异色 + 边框），**不依赖仓库里的外部图片**。
- `maxPixelDelta()` / `changedPixelCount()` —— **整图**像素比较。
  **禁止只探单点像素**：纯色区内部对模糊不敏感，单点探测会把"编辑没发生"误判成"编辑生效"。
- `sendUndo()` / `sendRedo()` —— 发送**真实 Ctrl+Z / Ctrl+Y 键事件**（走 `ImageWindow::keyPressEvent`），
  **禁止**直接调 `undoPublic()` —— 那就退化成回声测试。
- `QtMessageRecorder` —— 记录 Qt 警告/严重错误。**一条能力路径不得产生未登记的 Qt 警告**。

**规则 5.9（已知缺陷必须钉在测试里，不许只写在报告里）**　已确认但尚未修复的缺陷，用 `QEXPECT_FAIL` 钉成 **XFAIL**：
- 缺陷还在 → 测试结果为 XFAIL，`docs/DEBT.md` 有对应登记条目。
- 缺陷修好 → 断言转为通过，`QEXPECT_FAIL` 失效 → **测试变红**，强制你把 `QEXPECT_FAIL` 删掉。
禁止用"跳过测试"或"降低断言强度"来藏缺陷（契约规则 9.4）。

## 6. 代码规范

**规则 6.1（禁止变更日志式注释）**　源码中不得出现 `P0-x fix:` / `阶段 N:` / `2026-09-xx:` / `P8.3.2 (...)` 之类的变更记录。它们属于 commit message。

**⟦CI⟧ 规则 6.1a**　扫描 `src/**/*.{h,hpp,cpp}`，命中变更记录式注释模式 → 报出。

**规则 6.2（注释只写"为什么"与不变量）**　不写"已完成/已修复/Default is X"这类会随实现漂移的陈述。
- ❌ `// Default is OFF`
- ✅ `// The compositor path is the default since P8.2; fall back with setCompositorEnabled(false). See docs/CONTRACTS.md#7.1`

**规则 6.3（注释与实现必须同 commit 同步）**　不一致时**优先删注释**，其次改注释。

**规则 6.4（不留"给未来的接口"）**　零调用者的 API 要么接线要么删除。"以后会用"不是理由。

**规则 6.5（禁止源码树备份文件）**　`.bak*` 一律进 `_backup_archives/`（已 gitignore）。

**规则 6.6（既有硬性约束，继续生效）**
- 禁止类前向声明 —— 用到的类必须直接 `#include` 头文件
- 不使用 `override` 关键字
- C++17 + Qt 6.11.1 + VS 2022/2026（vcvars64）
- 源码注释一律英文，不写中文注释
- 不用 `QStringLiteral` 构造中文（会乱码），用 `QString("中文")` / `QString::fromLocal8Bit`
- Qt 6 下 `slots` / `signals` / `emit` 是保留宏，不可作标识符
- `cv::Scalar(200)` 只设第一个通道，四通道需逐通道赋值
- 不用 PowerShell 改源码（用 Read/Write/Edit 工具或 Python）
- 删除文件必须走 `mavis-trash`（Windows: `rm -- "<绝对路径>"`，一次一个目标）

**规则 6.7（禁止重复逻辑）**　相同或近似逻辑只允许存在一份。发现重复立即抽取，并给 CI 规则 3.5a 补检测。

## 7. 状态与真相不变量（项目级契约）

> 这些是**架构级**的约定，不是建议。每条都应有守护测试（规则 5.4）。
> 当前实现与本节的偏差本身是待办项，见 `docs/DEBT.md`。

### 7.1 像素真相

- **INV-PIXEL-1**　`LayerStack` 是像素的唯一真相来源。
- **INV-PIXEL-2**　`ImageWindow::m_current` **只是只读渲染产物**，任何编辑路径都不得写入它。
  *当前状态：❌ 未达成（审计 §7.1：m_current 同时是渲染缓存与可编辑画布，派生 04-02 / 05-02 / 05-03 / 05-10 / 05-15 / CP-11 / 05-30 / 05-36）*
- **INV-PIXEL-3**　所有编辑必须走「命令 → 修改目标图层 → 触发重合成」。
- **INV-PIXEL-4**　保存写出的数据必须与"当前用户看到并编辑的那份"一致，不得使用过期缓存。

### 7.2 对象身份

- **INV-ID-1**　图层身份只用 `LayerId`（单调递增 64 位），**禁止**混用对象地址、`int` 下标、`cv::Mat::data` 像素指针。
  *当前状态：❌ 三种混用（LYR-06 / LYR-12 / LYR-16）*
- **INV-ID-2**　`m_groups` 等以对象为 key 的容器必须改用稳定 id。

### 7.3 编辑原子性（撤销架构）

- **INV-UNDO-1**　全部命令遵循同一接口；`redo()` **必须**幂等重放，**禁止** no-op。
- **INV-UNDO-2**　命令只持 id + 最小 before/after 差异，禁止整图快照（超 8MP 必须 ROI/patch）。
- **INV-UNDO-3**　所有 undo/redo 统一经 `Document::notifyChanged()` 收尾（emit + invalidate + repaint）。
  *当前状态：❌ 4 种命令风格并存，redo 多为 no-op（LYR-07 / LYR-08）*

### 7.4 状态所有权

- **INV-STATE-1**　每个可观察状态有唯一 owner，视图只订阅不缓存副本。
  *当前状态：❌ 前景/背景色 3 份、工具配置 3 份、面板显隐 2 份、Quick Mask 3 份、选中图层 2 份、主题 2 份、窗口模式 2 份（审计 §7.6）*

### 7.5 生命周期与所有权

- **INV-LIFE-1**　跨对象持有一律用 `QPointer`（QObject）或 `shared_ptr`/`weak_ptr`（非 QObject），**禁止**裸指针。
- **INV-LIFE-2**　异步回调的 `invokeMethod` context **必须是接收者本身**，不得用 `qApp`；回调内必须用 `QPointer` 守卫。
- **INV-LIFE-3**　析构必须作废在飞任务（generation token / task id 自增）。
  *当前状态：❌ CI-03 / 05-04 / LYR-10 三处独立命中同一根因*

### 7.6 通道与格式契约

- **INV-FMT-1**　通道数、位深必须显式声明并在每个边界做校验，**禁止**默认按 3 通道处理。
- **INV-FMT-2**　`cv::Mat` → `QImage` 的格式必须与 `channels()` 一一对应（4 通道用 `Format_RGBA8888`，1 通道用 `Format_Grayscale8`）。
  *当前状态：✅ M1-3 已修 `matToQImage()` / `qImageToMat()`（`ImageProcessor`）*

### 7.6.1 图层像素与蒙版契约（M1-3）

这一节的实现在 `src/media/imageworker/layers/PixelFormat.h`（契约正文）与
`LayerMaskRenderer.h`（蒙版折算）。下面是**可断言的规则**，测试见
`tests/tst_AlphaMask.cpp`。

#### 像素模型

- **INV-PIXEL-1**　栈内图层像素（`Layer::image`）**一律** `CV_8UC4` BGRA，**直通 alpha**（非预乘）。
  归一化只允许走 `layers::toBgra()`；**禁止**自己 `cvtColor` 补 alpha —— 各种补法的 alpha 语义不同
  （255 / 0 / 保留原值），混用会让"半透明退化成乘黑"（CP-07）复发。
- **INV-PIXEL-2**　合成用 Porter-Duff `over`：

  ```
  cov    = src.a * 图层不透明度
  out.a  = cov + dst.a * (1 - cov)
  out.rgb = (src.rgb * cov + dst.rgb * dst.a * (1 - cov)) / out.a
  ```

  混合模式**只**决定 `src.rgb` 怎么算，**不**决定 alpha 怎么算。
- **INV-PIXEL-3**　图层不透明度（`Layer::opacity`）缩的是**覆盖度**，不是颜色。
  缩颜色等于把图层预乘，合成时会二次变暗。

#### 蒙版模型

- **INV-MASK-1**　蒙版**唯一**模型是 `Layer::mask`（`LayerMask` 结构体）。
  旧的 `cv::Mat layerMask` + `bool maskEnabled` 两份独立状态**已删除**，不得复活。
- **INV-MASK-2**　蒙版是灰度 `8UC1`，**不直接参与合成**。它由
  `LayerMaskRenderer::buildAlpha()` 折算成覆盖度，再由 `LayerMaskRenderer::applyAlpha()`
  写进源层的 alpha：

  ```
  out.a = pixel.a * coverage / 255
  ```

  蒙版与像素 alpha **只有这一个汇合点**。
- **INV-MASK-3**　蒙版**只改 alpha**，**不改颜色**。蒙版盖上去变黑 = CP-07 复发。
- **INV-MASK-4**　蒙版的密度 / 羽化 / 反相 / 显隐改动**必须可撤销**，
  即经 `LayerMaskCommand`（before/after 快照）入撤销栈（LYR-41）。

#### 渲染路径

- **INV-PATH-1**　两条渲染路径（`LayerStack::renderLegacy()` 与
  `LayerStack::renderViaCompositor()`）对同一个图层栈**必须**输出相同像素
  （`tests/tst_P8_RenderParity.cpp` 钉住）。
- **INV-PATH-2**　渲染循环**覆盖全栈**（LYR-13 / LYR-14）：底图是普通图层，
  不是根；隐藏底图真的会露出下面的内容。文档画布是**不透明白**（alpha = 255）。

### 7.7 依赖方向

- **INV-DEP-1**　依赖单向：`core → media/base → media/layers → media/render → media/tools → ui → app`。
- **INV-DEP-2**　**禁止** target 之间循环 include + 互相 link；公共头不得泄漏 `opencv2/core.hpp`。
  *当前状态：❌ `vistella_media` ↔ `vistella_ui_dock` 循环（审计 §7.8）*

## 9. 汇报规范

**规则 9.1（不自划阶段）**　AI 提出**按用户能力排序的能力清单**，由用户拍板。不得自行宣布"进入下一阶段"。

**规则 9.2（不自宣布完成）**　完成判定 = §1.2 四道门禁全绿 + 能力路径演示。

**规则 9.3（结论必须带范围）**　禁止只写"全绿 / 没问题 / 好了"。必须附：
- 覆盖了哪几条用户路径
- **没有验证什么**（盲区清单）
- 本次改动是否需要 ASAN / 人工验证

**规则 9.4（不隐藏失败）**　测试失败、构建失败、发现新缺陷，必须**主动报告**，不得在交付里静默跳过。

**规则 9.5（审计进清单）**　审计发现的 P0 必须进入下一阶段能力清单，不能只躺在报告里。

**规则 9.6（提交信息写"做了什么"，不写"要做什么"）**　提交信息的主体是**本次工作内容**，分三段：

1. **新增了什么** —— 新增了哪个类 / 模块 / 文件，用于实现什么功能。
2. **修改了什么** —— 改了哪个功能里的哪个 bug，改动前后行为差异。
3. **删除 / 替换了什么** —— 哪些代码不再使用被删除，替换成了什么。确实没有删除就写"（无代码删除）"。

**禁止**把阶段计划、"下一步做什么"、"待办"、"需要用户拍板"写进提交信息 ——
那些属于 `docs/DEBT.md` 与阶段能力清单。**提交信息是历史记录，不是会议纪要。**

自检：写完提交信息后搜一遍有没有 "will / next / TODO / 待办 / 需要拍板" 这类**面向未来**的表述，有就删掉。
